A. CHAPTER TWO - THEORETICAL FRAMEWORK AND AUTHORS
===============================================================================
Chapter Two builds the theory in six parts and then reviews five related works.

A1. Hotel management and reservation systems
    - Williams and Micheal (2018): manual room management is tedious; a
      database-driven reservation system stores, retrieves and relates records
      efficiently; object-oriented development gives maintainable, reliable,
      scalable software. Three-tier architecture, database normalised to 3NF.
    - Mwandila (2026): online reservation system for a hotel and its branches;
      availability check + streamlined booking + staff backend improve
      operational efficiency and guest experience.
    - Both separate the guest-facing booking process from the staff-facing
      management process, and relate a reservation to a ROOM TYPE (not a single
      room). This is the model adopted here: guests reserve room types and
      quantities; physical rooms are assigned later at the front desk.

A2. Web application architecture and the REST style
    - Fielding (2000): REST - resources identified by URIs, a uniform interface
      of standard methods, self-descriptive representations, scalability,
      independent deployment. Basis for the versioned /api/v1 JSON API.
    - Gamma, Helm, Johnson and Vlissides (1994): Design Patterns - name and
      separate responsibilities so designs are reusable.
    - Sommerville (2016): architectural design identifies principal components,
      their relationships and the principles that govern them. Basis for the
      four logical layers and the enforced dependency direction.

A3. Relational databases and concurrency control
    - Kleppmann (2017): concurrency and isolation are central difficulties of
      data-intensive applications.
    - PostgreSQL Global Development Group (n.d.): row-level locking (SELECT ...
      FOR UPDATE) so rows read cannot be changed until the transaction ends.
    - Microsoft (2023): optimistic concurrency in EF Core - a concurrency token
      is checked on save and a conflict is raised.
    - The system uses BOTH: pessimistic row locks for availability-affecting
      operations (booking creation, assignment) and an optimistic concurrency
      token for edits such as room types.

A4. Authentication, authorisation and application security
    - OWASP Foundation (2021): OWASP Top 10; the first two entries are Broken
      Access Control and Cryptographic Failures.
    - Response in this system: server-side role-based authorisation through
      named policies; modern password hashing; short-lived access tokens plus a
      refresh token stored only as a hash; no disclosure of whether an account
      or email exists; email verification before an account is created; the
      verification code is hashed and compared in constant time; lockout after
      repeated failed sign-ins.

A5. API contract conventions and reliability
    - Nottingham and Wilde (2016): RFC 7807 Problem Details - a standard,
      machine-readable error body. Adopted for every error, plus a
      machine-readable code (for example booking.insufficient_availability).
    - Kleppmann (2017): design for predictable behaviour in the presence of
      faults. Reflected in idempotent inventory-changing operations and
      validation at the API boundary.

A6. Agile software development
    - Beck et al. (2001): the Agile Manifesto - working software, close
      collaboration with the customer, responsiveness to change, over
      comprehensive documentation and rigid plans.
    - Sommerville (2016): agile methods deliver functionality in short
      incremental cycles and suit projects whose requirements evolve.

A7. Related works reviewed (Section 2.2)
    - Academic 1 - Mwandila (2026), Lundazi Castle Hotel online reservation
      system. Strength: combines availability check with a staff management
      interface. Limitation: does not describe the concurrency control that
      prevents two simultaneous reservations consuming the same capacity.
    - Academic 2 - Williams and Micheal (2018), Grand Ville Hotels reservation
      management system. Strength: well-normalised reservation database and a
      layered architecture. Limitation: does not address concurrent access to
      availability and has no live online guest channel.
    - Commercial 1 - Booking.com (n.d.), an online travel agency marketplace.
      Strength: scale, inventory, reviews. Limitation: matches many suppliers
      with many consumers; it does not manage one hotel's internal operation
      (assignments, check-in/out, payment records).
    - Commercial 2 - Cloudbeds (n.d.), a cloud property management system.
      Strength: breadth and integration. Limitation: subscription priced per
      room per month and broader than a small property needs.
    - Open source - QloApps (n.d.), PHP and MySQL hotel platform. Strength: free,
      auditable, self-hostable. Limitation: different stack and a general
      configuration not tailored to one property's rules.

A8. The research gap (Section 2.3)
    No reviewed system combines, in ONE owned system for ONE small property:
      (1) backend-authoritative availability AND pricing,
      (2) explicit concurrency control that prevents overbooking,
      (3) a complete front-desk workflow (assign, check-in, check-out, payment),
      (4) an online guest channel.
    The proposed system addresses exactly this combination.

A9. JUSTIFICATION - WHY THE CLIENT SHOULD PREFER THIS SYSTEM OVER THE COMMERCIAL
    ALTERNATIVES
    This is the justification / relevance material the project format requires (the
    proposal's "justification for the work", Chapter One's significance, and Chapter
    Two's "gaps in current solutions, cost"). It answers the question a panel or the
    client will ask: why not simply pay for Booking.com or Cloudbeds, or install the
    free QloApps?

    What each alternative actually costs the hotel:
    - Booking.com (online travel agency / marketplace). Charges a commission on every
      booking (commonly in the region of 15 to 25 percent). The guest relationship and
      the booking data belong to the platform, not the hotel. It publishes availability
      but does NOT run the hotel's internal operation - room assignment, check-in,
      check-out or payment recording - so a hotel that relies on it alone still needs a
      separate management system. It is therefore not a substitute; at best it is an
      extra marketing channel, and an expensive one.
    - Cloudbeds (commercial cloud property management system). A subscription priced
      per room per month, so the cost recurs and grows with the hotel. Much of its
      capability - channel manager, revenue management, central reservation,
      multi-property - is surplus to a small single property. The data is hosted by the
      vendor and features and pricing are controlled by the vendor, which is a form of
      lock-in.
    - QloApps (open-source platform). The licence is free, but it is built on a
      different stack (PHP and MySQL), it is a large general platform whose behaviour is
      not tailored to this hotel's rules, and it still requires hosting, configuration
      and maintenance expertise. It is oriented towards running a public booking website
      rather than a hotel's specific internal workflow.

    Why the client should prefer the system delivered here:
    1. Cost: owned, not rented. It is built once, with no subscription, no per-room
       monthly fee and no per-booking commission. The booking channel costs the hotel
       nothing per reservation. The only optional third-party cost is image hosting
       (Cloudinary), and even that is optional.
    2. Ownership of data. The hotel keeps its own database, its guest records and its
       booking history. No third party holds or monetises the guest relationship.
    3. Tailored to the hotel's own rules. The cancellation window, the no-show handling
       and the duration-based overstay surcharge are implemented directly for this hotel
       instead of forcing a general product to behave differently or buying modules it
       will not use.
    4. Right-sized functionality. It implements exactly the subset a small hotel needs -
       room inventory, date-based availability, online and walk-in booking, the
       front-desk workflow, payment recording, administrative reports and an audit log -
       without the surplus complexity that raises cost and staff training time.
    5. No vendor lock-in. The source belongs to the client (under the agreed terms), it
       runs on a low-cost server, and any competent developer can modify or extend it
       using mainstream technologies.
    6. Reliability that matters. Availability is authoritative on the server and is
       protected by database row locks and idempotent booking creation, so the last room
       cannot be sold twice. A hotel cannot see how a marketplace protects against
       overbooking; here the control is explicit and documented.
    7. Own-brand guest channel. The public booking site carries the hotel's own identity,
       which encourages direct bookings and avoids commission.
    8. One system replaces a patchwork. It replaces paper/spreadsheet records plus an
       online-agency listing with a single owned application.
    9. Security by design. Role-based authorisation on the server, hashed credentials,
       short-lived access tokens with a hashed refresh token, email verification and a
       lockout policy, following the guidance of the OWASP Top 10.
    10. Maintainable and extensible. A four-layer architecture enforced by automated
        tests, on a modern mainstream stack (C#/.NET, React) with a wide talent pool, so
        the system can be maintained after the project ends.

    Balanced caveat (state this honestly if asked): the commercial platforms exceed this
    system in breadth of features, around-the-clock vendor support, proven scale,
    pre-built integrations and multi-property handling, and a large hotel chain would
    still be better served by a commercial property management system. For a single
    small property that values ownership, the absence of recurring licence costs and its
    own operational rules, the delivered system is the better fit. This is the same
    balanced conclusion reached in Chapter Two, Sections 2.3 and 2.3.2, and in Table 2.1.

    One-line summary: owned, not rented; tailored, not generic; the hotel keeps its data
    and its margin.

B. METHODOLOGY - AGILE
===============================================================================
- Adopted methodology: agile (Beck et al., 2001; Sommerville, 2016), reported in
  Section 2.1.6 and applied in Section 3.1.1.1.
- The study is applied design-and-implementation research: the problem was
  defined from the actual operation of a small hotel, a design was proposed, and
  the design was realised and then examined against the problem.
- The system was built in verifiable increments. Each increment delivered a
  working slice (for example the room inventory, the availability search, then
  booking creation) and was tested before the next increment began; a set of
  automated tests was run to confirm that an increment had not broken an earlier
  one, so the growing system remained in a working state.
- Requirements were established from the case study's operation and from the
  published literature, and were refined as the design became clearer - which is
  precisely the situation agile methods suit.

D. HOW THE SYSTEM WAS ORCHESTRATED AND BUILT
===============================================================================
D1. Overall shape
    - TWO separately deployed applications:
        * Backend: an ASP.NET Core Web API on .NET 9, exposing a versioned REST
          contract under the path api/v1.
        * Frontend: a React single-page application written in TypeScript and
          built with Vite, served independently as static files.
    - The backend is the authority for availability, price and state. The
      frontend renders what the backend reports and never computes availability
      or price itself.

D2. Layered backend (one assembly, four namespaces)
    - Api layer         - controllers, routing, auth policies.
    - Application layer - use-case services and validation.
    - Domain layer      - entities, business rules, pricing.
    - Infrastructure    - EF Core, Identity, JWT, mail, media.
    - The allowed dependency direction is Api -> Application -> Domain, with
      Infrastructure implementing Application interfaces. It is ENFORCED by
      three architecture tests (NetArchTest) that fail the build if an arrow is
      reversed:
        (1) Domain depends on no outer layer.
        (2) Application does not depend on Infrastructure or Api.
        (3) Infrastructure does not depend on Api.
    - This is the single most defensible piece of engineering evidence: the
      architecture rule is executable, not just a diagram.

D3. API surface
    - 10 controllers and 66 endpoints, grouped by actor and module:
      Admin (25), Auth (9), Me/customer (8), Reception (15), RoomTypes (2),
      Availability (1), Pricing (1), Bookings (3), StayPolicy (1), Uploads (1).
    - Server-side role-based authorisation through named policies
      (AdminOnly, CustomerOnly, Staff). The client is never trusted to decide
      permissions.

D4. Data model and schema evolution
    - 15 entity types (data dictionary, Table 3.2) including RoomType,
      RoomTypeSurchargeTier, Room, Booking, BookingRoomType, RoomAssignment,
      Guest, Payment, User/Role, Setting, Notification, ActivityLog,
      PendingRegistration, PasswordResetCode.
    - Two deliberate link kinds: a database-enforced foreign key (only three:
      Booking->Guest, PasswordResetCode->User, RoomTypeSurchargeTier->RoomType)
      and a logical link (an indexed Guid column with no DB constraint). This is
      shown in the ERD by solid vs dashed lines.
    - The schema is created and evolved through NINE ordered EF Core migrations,
      never by editing the database by hand; a new environment is brought to the
      current shape by applying the history in order.

D5. Correctness controls
    - Overbooking prevention: booking creation and room assignment take
      pessimistic row locks on the relevant room-type rows in ascending
      identifier order inside a transaction, re-compute availability, and
      proceed only if capacity is still sufficient. Consistent lock ordering
      avoids deadlock.
    - Idempotent booking creation: a client-supplied Idempotency-Key is stored
      uniquely on the booking; a replayed request returns the original booking,
      and the same key with a different body is rejected. This makes retries
      after a network failure safe.
    - Validation at the API boundary; every error is a Problem Details body
      (RFC 7807) with a machine-readable code.

D6. Pricing
    - Money is stored as a fixed-precision decimal rounded to two places.
    - A booking total is the sum of its line subtotals, with no tax, service
      charge or fee (the hotel does not levy one).
    - Client-submitted prices and totals are IGNORED; the server recomputes them,
      so a caller cannot alter the amount by editing the request.
    - Duration-based surcharge: RoomTypeSurchargeTier gives fixed-amount overstay
      bands (FromHours, ToHours, Amount) per room type; the late-check-out charge
      is computed from the tier.

D7. Background work
    - Two scheduled background services run outside the request cycle:
        (1) expire pending registrations that were not verified in time;
        (2) adjust booking statuses as time passes so that a lapsed reservation
            does not keep consuming availability.

D8. Frontend and tooling
    - React + TypeScript + Vite + Tailwind CSS + shadcn/ui components.
    - The API types are generated from the backend OpenAPI document
      (types:api), so the client is checked against the real contract.
    - Guard scripts keep the codebase honest: check:no-mocks (no mock data in
      production paths) and check:theme (design-token consistency).

D9. Testing and evidence
    - Domain unit tests: 61 executed successfully.
    - Architecture tests: 3 (the dependency rules above), executed.
    - Frontend checks: run successfully.
    - Integration suite (xUnit + Testcontainers, ~130 test methods across
      availability, booking, idempotency, pricing quote, reception, walk-in,
      time-aware stays and administration): NOT executed here because it needs a
      running PostgreSQL instance or Docker, which the environment did not have.
      The report states this plainly and makes no claim about its result.

E. ANTICIPATED DEFENCE QUESTIONS AND SHORT ANSWERS
===============================================================================
Q1. Why did you not build on an existing platform such as Cloudbeds or QloApps?
    They are either subscription-priced and broader than a small property needs
    (Cloudbeds) or built on a different stack with a general configuration
    (QloApps). The case study needs a small, owned system with its own
    operational rules (cancellation window, no-show handling, duration-based
    surcharge) implemented directly. This is the gap in Section 2.3.

Q2. How do you stop two guests booking the last room at the same time?
    Availability is re-checked inside the booking transaction under pessimistic
    row locks on the room-type rows, taken in ascending id order. The second
    transaction sees the first and is refused. Consistent ordering avoids
    deadlock. This is exactly the control the two academic systems did not
    describe.

Q3. What is idempotency and why does it matter?
    A booking carries a unique client-supplied Idempotency-Key. If a client
    retries after a network failure, the same key returns the original booking
    instead of creating a second one; the same key with a different body is
    rejected. It makes retries safe.

Q4. Why both pessimistic locks and optimistic concurrency?
    The right strategy depends on contention and the cost of an anomaly
    (Kleppmann, 2017). Availability-affecting writes use locks because the
    anomaly (overbooking) is severe. Low-contention edits such as a room type
    use a concurrency token to detect a lost update cheaply.

Q5. Prove the layering is real and not just a diagram.
    Three NetArchTest architecture tests fail the build if Domain depends on an
    outer layer, if Application depends on Infrastructure or Api, or if
    Infrastructure depends on Api.

Q6. How is the client prevented from cheating on price?
    The server ignores client-submitted prices and totals and recomputes the
    whole quote from room-type base prices and the surcharge tiers. Errors use
    RFC 7807 Problem Details with machine-readable codes.

Q7. What does the database actually enforce?
    Only three foreign keys are database-enforced (Booking->Guest,
    PasswordResetCode->User, RoomTypeSurchargeTier->RoomType). The rest are
    logical Guid links with no constraint; the ERD shows the difference with
    solid and dashed lines, and the report states it.

Q8. What is the duration-based price?
    A fixed-amount overstay ladder per room type (RoomTypeSurchargeTier:
    FromHours, ToHours, Amount). A late check-out is charged by the tier that
    the overstay falls into.

Q9. Was the system evaluated with real users or under load?
    No. There was no formal acceptance session with hotel staff, and no
    response-time or load measurements. The report states this and makes no
    performance or satisfaction claims.

Q10. Did the tests all pass?
    The domain unit tests (61), the architecture tests (3) and the frontend
    checks ran successfully. The integration suite did not run because it needs
    PostgreSQL or Docker, which were unavailable. The report distinguishes a
    suite that exists from one that was executed.

Q11. Why .NET and React rather than PHP (QloApps) or another stack?
    Strong static typing on both sides, a mature web framework with built-in
    Identity and EF Core, row-level locking available in PostgreSQL, and no
    licence cost. Static typing lets the frontend be checked against the API
    contract, which is generated from the backend's OpenAPI document.

Q12. Which methodology did you use and why is it appropriate?
    Agile. The requirements were expected to evolve as a small hotel's workflow
    became clearer, so the work proceeded in short, tested increments (Beck et
    al., 2001; Sommerville, 2016).

Q13. Why should the hotel prefer your system to Booking.com or Cloudbeds?
    Booking.com is a commission-paying marketplace that does not manage the
    hotel's internal operation, and Cloudbeds is a per-room monthly subscription
    with surplus features. This system is owned outright, carries no commission
    or subscription, is tailored to the hotel's own cancellation, no-show and
    surcharge rules, protects against overbooking with explicit concurrency
    control, and keeps the guest data with the hotel. For a single small property
    that is the better fit; a large chain would still prefer a commercial PMS.

Q14. QloApps is free - why not just use and adapt it?
    The licence is free, but QloApps is a large general platform on a different
    stack (PHP/MySQL), so it still needs hosting, configuration and maintenance
    expertise, and its behaviour is not tailored to this hotel's rules. The
    delivered system is right-sized for the property, tailored to its rules, and
    on a mainstream stack that its future maintainers can work in.

Q15. What is the cost advantage in one sentence?
    No per-booking commission and no per-room monthly subscription; the booking
    channel is owned, so every direct booking keeps the full room revenue with
    the hotel.

F. LIMITATIONS TO STATE HONESTLY
===============================================================================
1. The integration test suite was not executed (no PostgreSQL/Docker in the
   environment); concurrency correctness is supported by design and unit-level
   evidence, not by an executed concurrency test. Offer to run it where a
   database is available.
2. No acceptance testing with hotel staff; no measured user satisfaction.
3. No performance or load testing - no response-time claims are made.
4. Payments are recorded at the front desk; there is no online payment gateway.
5. Findings are limited to the single case study and are not generalised.
6. The Chapter Four interface figures (4.1-4.15) are placeholders; no running
   instance was available in this environment to capture screenshots. Replace
   the placeholders with real screenshots before submission if a database can be
   started.
7. A secret was found in a development file placed under version control during
   the work; the report draws the operational lesson that security depends on
   how a system is run as much as how it is written.
